# Panzer Project APIリソース管理ガイドライン

> **リソースは武器弾薬と同じ。有限であり、計画的な運用が勝利への道である。**
>
> 本ガイドでは、Panzer Projectにおけるエージェント稼働制御とモデル選択のガイドラインを解説する。

---

## 1. Active/Standby制の概要

### 1.1 なぜActive/Standby制が必要か

Claude APIには **レート制限**（Rate Limit）が存在する。24名のエージェントが同時に動作すると、
APIのリクエスト上限に達し、エラーが発生する可能性がある。

これを防ぐため、**同時稼働エージェント数を制限**し、待機状態のエージェントをローテーションさせる
**Active/Standby制**を導入している。

### 1.2 稼働状態の定義

| 状態 | 説明 | 動作 |
|------|------|------|
| **Active** | 稼働状態 | タスクを受け取り、実行可能 |
| **Standby** | 待機状態 | タスクを受け取らない。リソース消費なし |
| **Processing** | 処理中 | タスク実行中（一時的にActive枠を占有） |

### 1.3 active_agent_limit の設定

`config/settings.yaml` で同時稼働上限を設定する。

```yaml
active_agent_limit: 8  # 同時稼働可能なエージェント数
```

#### 設定値の目安

| エージェント総数 | 推奨 active_agent_limit | 理由 |
|-----------------|------------------------|------|
| 6名（司令部のみ） | 6 | 全員稼働可能 |
| 12名（司令部+1中隊） | 8 | 司令部全員 + 中隊から2名 |
| 18名（司令部+2中隊） | 10 | 司令部全員 + 各中隊から2名 |
| 24名（司令部+3中隊） | 12 | 司令部全員 + 各中隊から2名 |

**注意**: Claude APIのレート制限はアカウントによって異なる。
Tier 1 の場合、安全を考慮して `active_agent_limit: 8` を推奨。

### 1.4 状態遷移のトリガー

```
        【Active → Standby】
           │
           ├─ 中隊長からのStandby指示
           ├─ タスク完了後の自動Standby
           └─ リソース不足の検知

        【Standby → Active】
           │
           ├─ 中隊長からのActive指示
           ├─ 緊急タスクの発生
           └─ 他エージェントのStandby化による枠の空き
```

## 2. モデル使い分けの基準

### 2.1 3つのモデルの特性

Claude APIには3つのモデルがあり、**コスト・能力・速度**がトレードオフの関係にある。

| モデル | 特性 | コスト | 速度 | 用途 |
|--------|------|--------|------|------|
| **Opus** | 最高品質 | 高 | 遅 | 重要判断、複雑設計 |
| **Sonnet** | バランス型 | 中 | 中 | 通常作業、コード実装 |
| **Haiku** | 高速軽量 | 低 | 速 | 軽作業、検索、確認 |

### 2.2 Opus を使うべきケース

```yaml
model: opus
```

| ケース | 具体例 |
|--------|--------|
| **重要な判断** | プロジェクト方針の決定、技術選定 |
| **複雑な設計** | アーキテクチャ設計、データベース設計 |
| **品質の高いドキュメント** | ユーザー向けドキュメント、技術提案書 |
| **リファクタリング** | 大規模なコード整理、構造変更 |
| **バグ調査** | 複雑な不具合の原因究明 |

### 2.3 Sonnet を使うべきケース

```yaml
model: sonnet
```

| ケース | 具体例 |
|--------|--------|
| **通常のコード実装** | 機能追加、API実装 |
| **定型タスク** | CRUD実装、フォーム作成 |
| **テストコード作成** | ユニットテスト、E2Eテスト |
| **ドキュメント更新** | README更新、コメント追加 |
| **レビュー** | コードレビュー、設計レビュー |

### 2.4 Haiku を使うべきケース

```yaml
model: haiku
```

| ケース | 具体例 |
|--------|--------|
| **軽作業** | ファイル検索、パス確認 |
| **簡単な確認** | 構文チェック、フォーマット |
| **情報収集** | ログ確認、ファイル一覧取得 |
| **定型応答** | 定型的な報告、ステータス更新 |

### 2.5 model_override の設定

`config/settings.yaml` で役割ごとにデフォルトモデルを設定できる。

```yaml
model_override:
  hq:                      # 司令部
    miho: opus             # 大隊長は重要判断が多いためOpus
    maho: opus             # 副大隊長も戦略立案でOpus
  platoon1:
    default: sonnet        # 第1中隊はデフォルトSonnet
  platoon2:
    default: sonnet        # 第2中隊もデフォルトSonnet
  platoon3:
    default: sonnet        # 第3中隊もデフォルトSonnet
```

#### タスク単位でのオーバーライド

特定のタスクだけ別のモデルを使いたい場合、タスクYAMLで指定できる。

```yaml
task:
  task_id: subtask_001
  description: "複雑な設計書を作成"
  model_override: opus     # このタスクだけOpusを使用
```

## 3. 24名稼働時のレート制限回避戦略

### 3.1 問題の概要

24名全員が同時に稼働すると、Claude APIのレート制限に達する。
特に以下の状況でリスクが高い：

- 全員が同時にタスクを開始
- 大量のファイル読み込みが発生
- 長時間の連続タスク

### 3.2 回避戦略

#### 戦略1: 中隊ごとのローテーション

```
時刻  | HQ | 第1中隊 | 第2中隊 | 第3中隊 |
------|----|---------|---------|---------|
09:00 | ●  | ●●      | ○○      | ○○      |  ● = Active
09:30 | ●  | ●○      | ●●      | ○○      |  ○ = Standby
10:00 | ●  | ○○      | ●●      | ●●      |
10:30 | ●  | ●●      | ○○      | ●●      |
```

- 司令部（HQ）は常時Active
- 各中隊は2名ずつローテーション
- 合計稼働数 = 6（HQ）+ 2（中隊）= 8名以内

#### 戦略2: 優先度ベースのリソース配分

| 優先度 | 説明 | リソース配分 |
|--------|------|------------|
| **緊急** | ブロッキング問題、本番障害 | Opusを優先割り当て |
| **高** | 重要機能、期限が近い | Sonnetを優先割り当て |
| **中** | 通常タスク | Standbyから順次Active化 |
| **低** | 改善、リファクタリング | リソースに余裕がある時のみ |

#### 戦略3: 自動Standby化

タスク完了後、一定時間（例: 5分）新しいタスクがなければ自動的にStandby化する。

```yaml
auto_standby:
  enabled: true
  idle_timeout: 300  # 秒単位（5分）
```

## 4. 中隊長のリソース管理フロー

### 4.1 中隊長の責務

中隊長は **部下のリソース状態を監視**し、適切に稼働状態を制御する責任を持つ。

| 責務 | 説明 |
|------|------|
| **稼働監視** | 部下のActive/Standby状態を把握 |
| **状態制御** | Active/Standby指示を出す |
| **負荷分散** | タスクを均等に分配 |
| **エスカレーション** | リソース不足時に司令部に報告 |

### 4.2 部下の稼働状態監視

中隊長は定期的に部下の状態を確認する。

```bash
# 自分の中隊の稼働状態を確認
tmux list-panes -t panzer -F '#{pane_index} #{@agent_id} #{@status}'
```

出力例：
```
0 darjeeling active
1 erika active
2 orange_pekoe standby
3 koume standby
4 assam standby
5 rukuriri standby
```

### 4.3 Standby指示の判断基準

#### Standbyにすべきケース

| ケース | 理由 |
|--------|------|
| タスクが長期間ない | リソースの無駄 |
| 他中隊のタスクが急増 | リソースを譲る |
| レート制限警告が出た | システム保護 |
| 低優先度タスクのみ | 緊急タスクに備える |

#### Activeにすべきケース

| ケース | 理由 |
|--------|------|
| 緊急タスクが発生 | 即座に対応が必要 |
| タスクキューが溜まっている | 処理速度向上 |
| 他中隊がStandby化した | 空いた枠を活用 |

### 4.4 状態変更の指示方法

中隊長は部下に対して、tmux経由で状態変更を指示する。

```bash
# 部下をStandbyにする
tmux send-keys -t panzer:0.2 '【中隊長より】一時Standbyに入れ。指示があるまで待機せよ。'
tmux send-keys -t panzer:0.2 Enter

# 部下をActiveにする
tmux send-keys -t panzer:0.2 '【中隊長より】Active状態に復帰せよ。タスクを割り当てる。'
tmux send-keys -t panzer:0.2 Enter
```

### 4.5 リソース不足時のエスカレーション

中隊長がリソース不足を検知した場合、司令部（みほ/まほ）にエスカレーションする。

#### エスカレーションの基準

| 状況 | エスカレーション先 | 対応 |
|------|-------------------|------|
| 中隊全体がキューで溢れている | 副大隊長（まほ） | 他中隊からの応援要請 |
| レート制限エラーが頻発 | 技術参謀（麻子） | システム設定の見直し |
| 緊急タスクだがリソース不足 | 大隊長（みほ） | 全体優先度の再調整 |

#### エスカレーション報告フォーマット

```yaml
escalation:
  from: darjeeling           # 報告者
  to: maho                   # エスカレーション先
  reason: resource_shortage  # リソース不足
  details: |
    第3中隊、現在6名全員がタスク実行中。
    新規タスクが3件キューに溜まっているが、
    active_agent_limit に達しており、追加稼働不可。
  request: |
    他中隊からの応援、または優先度の再評価を依頼したい。
```

## 5. 実践例

### 5.1 シナリオ: 緊急バグ修正が発生

```
【状況】
- 本番環境で重大なバグ発見
- 第2中隊のノンナ（バックエンド担当）が最適
- 現在、active_agent_limit = 8 で全枠埋まっている

【対応フロー】
1. カチューシャ（第2中隊長）が状況を判断
2. 優先度の低いタスク実行中のクラーラをStandbyに
3. ノンナをActiveに変更
4. ノンナにバグ修正タスクを割り当て
5. model_override: opus でタスク実行（品質重視）
```

### 5.2 シナリオ: 大量の軽作業が発生

```
【状況】
- ドキュメントの軽微な修正が20件
- Sonnetを使うとコストが高い

【対応フロー】
1. みほ（大隊長）が判断
2. 各中隊から1名ずつ、計3名をActive化
3. 各タスクに model_override: haiku を設定
4. 並行して高速処理
5. 完了後、自動Standby化
```

### 5.3 シナリオ: 平常時の運用

```
【状況】
- 通常のタスクが断続的に発生
- 特に緊急性はない

【対応フロー】
1. 司令部6名は常時Active
2. 各中隊は2名ずつActive（計6名）
3. 合計12名で active_agent_limit = 12
4. タスク完了後、5分で自動Standby
5. 新規タスク発生時に必要な人数だけActive化
```

## 6. トラブルシューティング

### 6.1 レート制限エラーが発生した場合

#### エラーメッセージ例
```
Error: Rate limit exceeded. Please try again later.
```

#### 対処法

1. **即座にStandby化を実行**
   - 全中隊の副中隊長をStandby化
   - active_agent_limit を一時的に下げる（例: 12 → 8）

2. **タスクの優先度を見直し**
   - 緊急タスクのみ継続
   - 低優先度タスクは保留

3. **モデルを下げる**
   - OpusをSonnetに変更
   - SonnetをHaikuに変更

### 6.2 全員がStandbyでタスクが進まない

#### 原因
- 中隊長の判断ミス
- 自動Standby化の設定ミス

#### 対処法

```bash
# 強制的に全員をActive化（緊急時のみ）
for i in {0..23}; do
  tmux send-keys -t panzer:0.$i '【司令部より】全員Active化せよ'
  tmux send-keys -t panzer:0.$i Enter
done
```

### 6.3 特定のエージェントだけ遅い

#### 原因
- モデル設定が適切でない（Opusで軽作業をしている等）
- タスクの複雑度が想定より高い

#### 対処法

1. タスクのmodel_overrideを見直す
2. タスクを分割して複数人で並行処理

## 7. まとめ

### リソース管理の鉄則

1. **司令部は常にActive、中隊はローテーション**
2. **タスクに応じて適切なモデルを選ぶ**
3. **レート制限を超えないよう稼働数を制御**
4. **中隊長がリソースを監視・制御する**
5. **緊急時は優先度ベースで再配分**

### 推奨設定（24名稼働時）

```yaml
# config/settings.yaml

active_agent_limit: 12   # 司令部6名 + 各中隊2名

model_override:
  hq:
    miho: opus           # 大隊長
    maho: opus           # 副大隊長
    yukari: sonnet       # 情報参謀
    saori: sonnet        # 通信参謀
    hana: sonnet         # 記録参謀
    mako: sonnet         # 技術参謀
  platoon1:
    default: sonnet
  platoon2:
    default: sonnet
  platoon3:
    default: sonnet

auto_standby:
  enabled: true
  idle_timeout: 300      # 5分
```
